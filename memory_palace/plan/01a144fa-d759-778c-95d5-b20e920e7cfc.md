## 待确定事项

- **C 的实现细化（需你确认）**：更干净的做法是「`pending` 存在且 `gap ≥ 30min` → 直接丢弃 pending」，纯确定性、无需额外决策调用；而不是「靠话题切换判定来清」。理由：确认提示的语义有效期本就等于这个 gap。
- `topic_switch` 的 `state` 传什么：仅当前消息？还是「上一条用户消息 + 当前消息」？还是最近 3 轮？（越少越省 token，建议先「上一条 + 当前」）
- 时间块用独立 `system` 条目；若 DeepSeek 不接受多条 system，回退为「当前 user 消息的一行前缀」——**待实测验证**
- `CHAT_HISTORY_LIMIT=20` 是否维持？跨天时 20 条可能全是昨天的（与话题切换共同暴露，但本次不做 L3）
- 时区固定 `Asia/Shanghai`，还是可配（`TZ` / `CHAT_TZ`）？容器默认 UTC 是现存隐患
- 30min 门控只对 chat 路径生效（dev / 游戏路径不做时间注入）——请确认
- 数值标注：30min、`0.7`、（决定不做的）延迟预算均为**工程经验值**，`docs/conventions/external-constraints.md` 中无对应外部约束 → 一律可配 + 标「经验值，非外部约束」
- 话题切换阈值是否要沿用三档置信度（高/中/低）？本次设计为单阈值（`≥0.7` 即切换，否则不切），确认是否够用
