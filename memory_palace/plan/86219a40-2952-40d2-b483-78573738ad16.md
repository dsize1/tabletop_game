# 计划：测试需求

## 计划
针对「测试需求」，本轮先把测试基线补齐，避免直接增加用例造成重复或遗漏。整体分三步推进：
1. **基线梳理**：盘点仓库现有测试目录、运行命令、CI 配置与覆盖率现状，形成 `docs/testing-baseline.md`，作为后续所有工作的参照。
2. **分层补测**：按单元测试（规则引擎、状态机、序列化）→ 集成测试（单局完整流程）→ 契约测试（对外接口）的顺序补充用例，并为每层准备共享夹具与工厂，避免用例之间互相依赖。
3. **工程化接入**：统一测试脚本入口、覆盖率报告与 CI 工作流，并把已修复缺陷登记到回归清单，保证后续改动可复用。
各层的测试框架、覆盖率阈值、是否包含 UI/E2E 与性能测试等尚未确定，统一记录在「待确定事项」，不在本计划中假定具体数值。

## 待确定事项
- 项目使用的语言与运行时，以及现有测试框架（Jest / Vitest / Pytest / 其他），决定上述配置文件名与命令写法
- 覆盖率阈值取值，以及是否对关键模块单独设阈值
- 是否需要 UI/E2E 自动化；若需要，目标运行环境与浏览器范围
- 是否需要性能/压力测试；若需要，指标口径（响应时间、并发规模等）由谁定义
- 是否存在外部依赖（模型接口、数据库、第三方服务）需要在测试中打桩，以及打桩的边界
- 测试数据的来源与合规要求（是否可使用真实对局数据）
- CI 平台的最终归属（GitHub Actions 或自建），影响工作流文件路径
- 「测试需求」的范围边界：是仅补自动化测试，还是同时包含手工测试用例与验收标准

## harness 优化项
- 在 harness 中固化标准测试命令入口（优先调用 `scripts/test.sh`），避免每次手工拼装命令
- 让 harness 输出结构化的测试结果摘要（通过/失败/跳过数量、首个失败用例路径），便于快速定位
- 为长耗时测试增加依赖缓存与增量运行支持，减少重复全量执行
- 在 harness 中增加「测试失败时自动附上复现命令」的默认行为
- 增加 harness 侧的变更影响分析：根据改动文件推荐需运行的测试子集
- 统一失败日志格式（用例路径 + 断言差异 + 复现命令），便于后续自动解析
