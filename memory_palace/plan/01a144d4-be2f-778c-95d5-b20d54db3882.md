# 计划文档

## 计划

1. 目标：意图决策引入「双置信度阈值 + 中带人工二次确认」三档——≥θ_high 直接按决策结果路由（同现状）；[θ_low, θ_high) 请用户确认，确认=是则按决策结果路由，=否则回落到低阈值逻辑；<θ_low 走现状（#前缀 → 默认 chat）。所有分支仍受 dev 白名单 / 规则引擎校验。
2. 阈值：沿用 DECISION_INTENT_THRESHOLD 作低阈值 θ_low（默认 0.6）；新增 DECISION_INTENT_THRESHOLD_HIGH 作高阈值 θ_high（默认 0.8）；启动校验 θ_high ≥ θ_low（否则告警并夹紧）。
3. 决策层保持纯函数：decision.ts 新增 confidenceBand(conf, low, high) -> "high"|"confirm"|"low"；decideIntent 在 confirm 档返回 via="confirm" + proposal{intent,confidence}（decision 层不做 IO）。
4. 确认状态：新增 src/intent-confirm.ts，Redis key intent:pending:{group}:{sender}，值 {intent,confidence,content,ts}，TTL INTENT_CONFIRM_TTL_SEC（默认 300s，依据=群被动回复窗口 5 分钟，已登记 external-constraints）；提供 load/save/clear + 纯函数 matchConfirmReply（是/否词表）。
5. 编排顺序（index.ts）：health → dev #前缀/#文档 硬判断（命中即清 pending）→ pending 命中「是/否」（用原消息执行/回落）→ decideIntent（high 直接路由；confirm 存 pending + 回确认提示；low 现状兜底）。
6. 复用执行体：把 intent switch 抽成 executeIntent(intent, content, ...)；确认=是时用原消息内容执行 proposal.intent。
7. 可观测：日志补 intent=… via=confirm proposal=<i>(<conf>)、confirm=yes intent=<i>、confirm=no → 兜底，弥补决策轨迹不可回溯（上一轮日志分析缺口）。
8. 文档：更新 docs/modules/agent-gateway.md（置信度兜底 + 配置表）、docs/architecture.md §6.1/§6.2、apps/agent-gateway/.env.example。
9. 测试：离线单测覆盖分档边界、confirm 分支、确认词表、pending 生命周期（假存根）。
10. 阈值探索结论（回放 205 条入站 / 181 条模型判定，与线上日志一致率 100%）：非 chat 正确预测 conf=0.840~0.965；非 chat 错判 conf=0.388~0.815（其中 ≥0.6 的 11 条落在 0.610~0.815）；确认集 [0.6,0.8) 内非 chat 预测 9 条 9 错（精确率 100%）。→ θ_low=0.6、全局 θ_high=0.8；θ_high 提到 0.85/0.90 会把正确 game 预测(≥0.84)拖进确认集，精确率跌到 73%/65%，不可取。
11. 命名与配置落地：功能称「意图确认」；新增 DECISION_INTENT_THRESHOLD_HIGH=0.8、INTENT_CONFIRM_TTL_SEC=300；引擎侧可选双阈值原语（缺省回落全局）。
12. 实现口径说明：点3/点4 交叉处按「非 y/n 且本身就是又一次中带请求 → 同 openid 覆盖（记异常）；否则首次追问、再次判 n」实现；matchConfirmReply 落在 intent-confirm.ts（非原计划的 decision.ts）。
13. 遗留：引擎自带双阈值（dev/game 各自 θ）尚未接入——当前决策意图分类统一走全局阈值；游戏动作置信度 `conf(action)` 路径本就未接入（§6.3 待拉斯维加斯）。
14. harness loop 完成：① chat.ts 三条回退路径补原因日志（无 key / 空正文含 model+thinking / 异常含 model+timeout）；② 新增 apps/scripts/replay-intent.mjs（node:sqlite 读 group_messages → 打决策服务 → 输出置信度分布与确认带触发量，验证复现上轮标定：确认带内 8 条全为线上已观测误路由）。
15. 确认链路语义澄清（用户提出）：一轮确认 = 2 次被动对话——①原问题 A → 确认提示（reply_msg_id=A，即「原问题的答复」）；②y/n（B）→ 按原问题执行的答复（reply_msg_id=B）。内容可在 group_messages 完整还原；chat_history 不记确认提示与 y/n。
16. 对应补强：PendingIntent 增加 cid=原问题 message_id；日志统一带 cid 并补齐终止行——via=confirm（发起）、via=confirm_yes（通过执行）、via=confirm_no（否决兜底）、意图确认=unknown/n（追问/判否），dev #前缀硬路由落 intent=dev via=prefix cmd=…。
17. 可观测补强（用户要求「记录结果和置信度」）：Decision 增加 model={意图,置信度}（决策模型原始输出，各支路都保留）；终结行统一为 intent=<最终> via=<路径> model=<候选>:<置信度> cid=<原msgId>，低带/中带否决另带 fallback=prefix|default；故由 via+model 即可反推是否进过确认带。原 proposal 字段统一更名为 model（decision.ts/index.ts/test-decision.mts/docs 同步）。
18. 【终结 2026-10-16 验收通过】交付：双阈值三档 + 意图确认 + 可回溯日志（model=/cid=）。离线验证全绿。遗留（转后续任务，不阻塞本次验收）：① QQ 真机验证中带 y/n 两路；② 引擎自带双阈值接口；③ 决策轨迹结构化事件（现有终结行已可解析）。
