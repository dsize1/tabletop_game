## 0. 结论先说（TL;DR）

1. **engines.txt 是一份「事件驱动 + 结算栈」的最小骨架**，方向对（事件化、服务器权威、播报队列），
   但离可承载 296 技能还缺 **9 大块**：牌区唯一归属、交互层（pending）、卡牌属性、窗口/主体、询问完整性、
   帧数据归属、伤害 vs 失体力、守恒、AI/视图投影。v2 已经把这些「补」出来了，但补的方式是**边做边补、
   机制分散在 30+ 个 hook 点**，这就是 v2 的病灶。
2. **V3 的正确起点不是重写 v2，而是把 v2 已经验证过的「机制词表 + 契约门禁」从『事后清单』升级为
   『引擎的骨架类型系统』**：技能不再是「各写一段 handler」，而是「声明式的 SkillDef + 统一 hook 注册表」。
3. **技能分类**（20 批次 296 技能）暴露 6 类「机制上难表达」的形状：
   转换技（阴阳，4）/ 多触发（25）/ 主动+触发并存（17）/ 多阶段窗口 / 授予技（含未注册的怀柔/清侧/排异）/ 主公技他人侧（13）。
   其中**转换技与「回合内主动 + 回合外响应」**两类建议**拆成多个独立「技能面（face）」**（见 §2.4），
   其余用「多 hook + 单一状态源」解决，不必硬拆。
4. **v2 已补齐的机制（49 条）基本覆盖标准身份局全部需求**，V3 直接继承为「机制注册表」，不重造；
   真正的欠账是 ① 手牌/武器特效抽象（武器=特殊技能注入）、② 授予技不是一等公民、③ 丢失的 v1 设定（大厅/身份/中断等，v2 后期才补）。
5. **V3 架构建议**：`spec（契约）→ kernel（9 区 + 事件 + 交互 + 守恒）→ mechanism registry（机制即数据）→
   skills（声明式 SkillDef 分面）→ view/ai（纯投影）`，内核零技能名、技能零牌名（延续 v2 已证明的门禁）。
6. **AI**：stable-baselines3 + PPO 在**信息不完全的身份局**上**不直接适配**（部分可观测 + 对手策略非平稳 +
   动作空间离散/合法集动态 + 局内目标因身份而异），建议 V3 先做「观测/动作/奖励三件套的规范接口」，
   中期用 **行为克隆蒸馏启发式 + 自对弈**过渡，PPO 仅作为「完美信息子问题」或「固定身份」实验（详见 §7）。

## 1. engines.txt 设想架构 vs v2 差异

### 1.1 engines.txt 里「对」的部分（V3 应保留）

| engines.txt | 解读 | V3 处理 |
|---|---|---|
| 一切动作先变 `GameEvent` | 事件溯源、可回放 | ✅ 保留（v2 已有，升级为「带窗口/主体快照」） |
| `GameState` 唯一真相源 | 服务器权威 | ✅ 保留（I2/硬约束 B） |
| `ResolutionChain` 嵌套结算 | 濒死/无懈嵌套的雏形 | ✅ 保留（升级为「帧 + 发起帧归属」） |
| `TriggerRule { when/condition/priority/handler }` | 技能声明式描述 | ✅ 方向对，但 handler 是 `fn` 指针 → 改成 trait + 注册表 |
| `narration_queue` 播报队列 | AI 主持/群侧播报 | ✅ 保留（V3 明确为「文案由状态机生成」） |

### 1.2 engines.txt 里「缺」的部分（v2 已补、V3 必须继承）

| 缺口 | 后果（engines.txt 会翻车处） | v2 现状 | V3 落点 |
|---|---|---|---|
| **牌区唯一归属**（9 类区） | `hand: Vec<CardId>` 之外牌不知道在哪；帧里暂存牌会凭空消失 | 9 区 + 守恒门禁 | 内核类型层（`Zone` 枚举） |
| **交互层（pending）** | 技能需要「选目标/多选/二选一」时，`handler → Vec<Effect>` 无法表达交互 | `Pending` + `PendingBuilder`（出口类型级强制） | 内核 |
| **卡牌属性**（类别/子类/颜色/点数/伤害属性/响应牌） | `CardKind` 只有 4 个枚举，`suit/number` 没有「伤害属性」「是否伤害锦囊」「响应牌」 | `CardDef` 字段化 | 生成物 `cards_generated` |
| **目标列表** | `targets: Vec<PlayerId>` 有，但无「每个目标可单独引用 + 目标指定事件」 | `target_chosen` 事件 + 列表 | 内核 |
| **伤害 vs 失体力** | `Damage` 一个事件，无法区分「造成伤害/失去体力/减上限」 | `flow::damage*` / `lose_hp` / `MaxHpChanged` 三出口 | 内核 |
| **询问完整性（I1）** | 无手牌直接结算，无「假犹豫」窗口 | `must_ask` + 门禁 C7 | 宪法 |
| **帧数据归属（硬约束 B）** | `stack.last_mut()` 会覆盖濒死帧 | 写发起帧 + `check_no_zombies` | 宪法 |
| **窗口/主体** | `when: fn(&GameEvent)->bool` 无法声明「谁的回合/阶段」 | `Window` + `subject` 声明 | 内核 |
| **AI/视图投影** | 无 | `view.rs`（三分区）+ `ai.rs`（决策点） | V3 纯投影层 |

### 1.3 engines.txt 与 v2 的「优劣」判断

- **engines.txt 的价值**：是一份**教学级最小闭环**（事件→触发→效果→播报），适合用来确认「事件驱动」的骨架方向。
- **engines.txt 的局限**：`Effect` 是「同步副作用」，无法表达 296 技能里最常见的**多步交互**（选牌→选目标→结算→切换面）；
  `TriggerRule` 用裸函数指针，无法承载「窗口/主体/优先级/注册表派生/覆盖校验」这些 v2 已经证明必须有的约束。
- **v2 的价值**：机制词表（49 条）+ 775 条裁定锚点 + 契约门禁 + 真实牌结算，这些是**不可丢弃的资产**。
- **v2 的病灶**（V3 要治的）：机制是「事后补丁清单」而非「骨架类型」；技能 handler 形态不统一
  （`skills/mod.rs` 1968 行 + 20 个 batch 文件，每个技能一套 `can_*` / handler / hook 各写一半，见 §2.5）。

**一句话**：engines.txt 给 V3 的是「事件化 + 结算栈」的**方向确认**；v2 给 V3 的是「必须满足的语义基线 + 机制词表」；
V3 要做的是**把词表变成类型系统，把 handler 变成声明**。

## 2. 技能分类（B0–B20 全量 296 技能）

> 数据：v2 注册表 `skills::SKILLS` 296 个（code 唯一）。`kind` 分布：
> `normal` 216 / `locked` 47 / `lord` 13 / `limited` 12 / `awaken` 8。

### 2.1 六类「机制难表达」形状（本次分类的核心产出）

| 类 | 数量 | 代表 | 机制缺陷 | V3 对策 |
|---|---|---|---|---|
| **A. 转换技（阴阳技）** | 4 | 拒战/审时/成略/贞良 | 两面各自有窗口，发动后切换；注册表里贞良的 yang/yin window 是 null（导出缺口）；拒战曾把阴面误写成他人回合 | **拆成两个 face**，每 face 独立声明窗口+触发，切换只换 face 指针 |
| **B. 多触发技能** | 25 | 审时(3)/激昂(3)/雷击(3)/良姻(2)/奋激(2) | 一个技能多个触发点，v2 用 `triggers: []` 数组，但各触发点的窗口/主体/条件各写一半 | 每个触发点 = 一个「订阅项」，`SkillDef.subscriptions[]` 声明式，各自带 window+subject |
| **C. 主动+触发并存** | 17 | 极奢(active+PhaseEnd)/挑衅(active+DamageAfter)/缔盟/明策/父魂 | 同一个技能既是回合内主动技、又是回合外响应——正是用户问的「拆不拆」 | **拆成 face**（主动面 + 响应面），共享单一状态源 |
| **D. 多阶段窗口** | 60+ | 极奢/明任/箜声/良姻 | 技能可出现在多个阶段（准备/结束/出牌） | window 声明参数化（`OwnPhase(Play)` 等），不靠触发点隐式决定 |
| **E. 授予技** | ~10 | 伪帝/化身/绝响/攻心/怀柔/清侧/排异/勤学觉醒 | 授予技**不是一等公民**：怀柔/清侧/排异不在注册表；文本靠 `GRANTED_SKILL_TEXT` 补丁 | 授予技也进 `SkillDef`，`skills::active` 单一查询（自带 ∪ 授予 ∪ 临时） |
| **F. 主公技他人侧** | 13 | 激将/护驾/颂威/兴衰/立军 | 曾是一条硬编码白名单 `LORD_SKILLS_USED_BY_OTHERS` → 新主公技拿不到他人侧 | 注册表模式（`LordSide` 枚举 + TABLE + 覆盖校验，ADR-0041 已示范） |

### 2.2 转换技（阴阳技）明细——拆分的直接证据

| 技能 | 阳面窗口 | 阴面窗口 | 触发 | 备注 |
|---|---|---|---|---|
| 拒战 `juzhan` | **OtherTurn**（他人回合） | **OwnTurn**（自己回合） | TargetChosen | 阳=回合外防御，阴=回合内摸牌，两面语义完全不同 |
| 审时 `shenshi` | OwnTurn | OtherTurn | TargetChosen + DamageAfter + PhaseStart | 主动 + 双触发，最复杂 |
| 成略 `chenglue` | OwnTurn | OwnTurn | 无（纯主动） | 两面同窗口，只是效果不同 |
| 贞良 `zhenliang` | （注册表 null，实际 OtherTurn） | — | CardUsed + CardPlayed | 导出缺口需修 |

**结论**：拒战/审时的「阳=回合外 / 阴=回合内」证明了**两面不是同一个技能的两个选项，而是两个独立技能面**。
v2 用一个 `transform` 标记 + 切换计数器硬扛，导致「拒战阴面误写成他人回合」「贞良 white list 漏注册」。
**V3 拆 face 是必要且正确的**（详见 §2.4）。

### 2.3 「回合内主动 + 回合外响应」并存——是否拆

样本（主动+触发并存的 17 个）：极奢、挑衅、缔盟、明策、父魂、镇骨、陷嗣、活墨、匡弼、放权、长标、渐营、燕语、贞良、激将、酒诗、审时。

- **应拆**（两面是独立语义，各自有独立资源/窗口）：贞良（主动面 vs 响应面）、审时、父魂、酒诗。
- **不拆**（主动只是同一效果的「手动入口」，响应是同一效果的「自动入口」）：极奢（主动发动=选择是否生效，PhaseEnd 是结算点）、挑衅（主动是入口，DamageAfter 是结果结算）、缔盟/明策（主动发起，伤害后结算，是「同一个技能的两步」而非两面）。

**判定口径**：拆与不拆的边界 = **「两面是否共享同一资源与同一玩家意图」**。共享 → 用「一个 SkillDef 多步骤」；不共享 → 拆 face。
建议 V3 提供 `SkillDef.faces[]`（每个 face 独立 window/triggers/subject），**默认单 face**，多 face 仅给转换技与明确的「主动+响应」类。

### 2.4 「技能拆段」的结论（回答用户点 1）

- **阴阳技（转换技）**：**必须拆**。每个面 = 独立 face（独立 window + 独立 hooks + 独立文案），切换 = 换 face 指针。
- **「同一技能回合内主动 + 回合外响应」**：**有条件拆**。按「是否共享意图与资源」判定（§2.3 口径）。
- **多触发（同技能多钩子）**：**不拆**，用 `subscriptions[]` 声明式表达，每个订阅带自己的 window/subject。
- **多阶段（极奢等）**：**不拆**，用 window 参数化 + 多步骤（steps[]）表达。
- **可多次修改（如连弩连击、巧说计数）**：**不拆**，用「计数器/状态 + 单一查询入口」表达。

> 拆 face 的直接收益：① 窗口/主体/触发在**声明处**校验，不再靠 handler 首行守卫；② 视图/legal/文案按 face 派生；
> ③ 转换态切换只是一个指针操作，不再散落 `yang_window`/`yin_window`/白名单。

### 2.5 为什么 v2 的 handler 形态是病灶（供 V3 设计引用）

v2 技能层（`skills/` 20 个 batch 文件，约 3.4 万行）反复踩的坑，根因是**每个技能 = 一套 `can_*` + handler + hook 各自实现**：

- 「同一规则两处各写一半」（legal/execute/view 三份清单）——需 **legal≡execute 同源 + 视图派生**；
- 「触发点逐路径硬编码」——需 **事件总线 + 动作差分**；
- 「就地压帧被父帧 pop」——需 **技能只返回 Step，栈只由内核改**；
- 「帧里暂存牌丢失」——需 **帧持牌落盘 + 守恒门禁**；
- 授予技漏注册——需 **授予技 = 一等公民的 SkillDef**。

这些对策 v2 已经**证明有效**（spike 6/6 缺陷注入检出、门禁绿），V3 把它们**固化为类型/门禁**，而不是再次「靠人守」。

### 5.3 v1 的「武器特效作为特殊技能注入」——V3 采纳

v1 定下的口径（用户点 4 提及）：**武器的特效不是写在牌结算的 `match` 里，而是作为「特殊技能」注入**。
即：每件武器/防具 = 一个 `SkillDef`（`kind=equip`），装备时 `grant`，卸下时 `revoke`，
特效全部走与武将技能**同一套 hook 注册表**。

**V3 落点**：
1. 装备 = 一个 `EquipSkill`，与 `SkillDef` 同构（有 `subscriptions`/`active`/`conversions`）；
2. 装备区变化 → `grant/revoke` 该 equip-skill（与授予技同一机制，见 §2.1-E）；
3. 牌结算**只读** `Game::armor()/weapon()` 单一入口，不 `match` 武器名；
4. 门禁：`tests/cards.rs::gate_kernel_has_no_card_name_branch` 覆盖武器名（v2 已证有效，V3 沿用并扩展）。

> 收益：新增武器（木牛流马、骅骝之外的新装备）只需注册一个 equip-skill，内核零改动；
> 武器特效的「窗口/主体/时序」复用技能的声明式校验，不再散落牌结算。

## 6. V3 引擎架构协商（可扩展）

### 6.1 分层（自顶向下）

```
specs/（语义宪法 I1-I3 + 契约 contracts/*.json + 机制词表 mechanics.json）
   ↓ 门禁：check:spec-conformance / check:sgs2-conventions（扩展为 V3 版）
kernel/（规则内核，零技能名、零牌名）
   ├─ zone（9 类区 + 守恒）
   ├─ event（事件 + window + subject + 快照）
   ├─ pending（交互描述符 + 出口类型级强制 + escape_mandatory）
   ├─ resolve（结算栈 + 帧 + 发起帧归属 + 单延迟队列）
   ├─ flow（伤害/失体力/回血/濒死/判定/数值链 唯一出口）
   └─ card_play（使用/目标/响应/无懈/延时/拼点 单一流程）
mechanism registry（机制即数据：49 条机制 → enum/表 + 覆盖校验）
skills/（声明式 SkillDef：faces[] + subscriptions[] + conversions + active）
   ├─ 武将技能（296 + 未来）
   ├─ 授予技（一等公民）
   └─ equip-skill（武器/防具特效，§5.3）
view/（纯投影：public_state / player_view / special_zones，I3 视图不判业务）
ai/（观测流 + 决策点枚举 + 剪枝 + 决策日志；为 RL 预留规范接口，§7）
```

### 6.2 内核 vs 技能的硬边界（延续 v2 已证明的门禁）

| 边界 | 约束 | 门禁 |
|---|---|---|
| 内核零技能名 | 内核不出现 `== "skill:"` / 技能 code | `gate_kernel_has_no_skill_branch` |
| 内核零牌名 | 内核不出现 `== "杀"` / `cards::def("…")` | `gate_kernel_has_no_card_name_branch` |
| 伤害单出口 | 牌/技能不得直写 `hp`，走 `flow::*` | `gate_card_play_never_touches_hp_directly` |
| 单延迟队列 | 禁止 per-skill 队列 | `gate_single_deferred_queue` |
| 技能不压栈 | 技能只返回 `Step` | spike 已证 |

### 6.3 技能模型（核心变更：从「handler」到「声明」）

```rust
struct SkillDef {
    code: &'static str,
    kind: SkillKind,            // normal/locked/limited/awaken/lord/equip
    faces: Vec<Face>,           // 默认 1 个 face；转换技/主动+响应类拆多 face
    active: Query,              // skills::active 单一查询（自带 ∪ 授予 ∪ 临时）
}
struct Face {
    window: Window,             // OwnTurn / OwnPhase(X) / OtherTurn / OtherPhase(X) / AnyTime
    subscriptions: Vec<Subscription>,  // { event, subject: Self/Other/By/From, priority, condition }
    hooks: Vec<Hook>,           // conversions / target_blocker / distance / sha_limit / hand_limit / dying / wuxie ...
    steps: Vec<Step>,           // 多阶段技能的时序（"然后" 连接的有序步骤）
    escape: Escape,             // escape / escape_mandatory（I1/强制步骤）
    present: Presentation,      // 文案由状态机生成（name/trigger text），禁止分支手写整句
}
```

**关键差异 vs v2**：
1. **face 化**：转换技/主动+响应类拆 face，窗口/主体/触发在声明处校验（治 §2 的 A/C 类）；
2. **subscription 带 subject**：每个订阅声明 `subject: Self/Other/By/From`，handler 首行守卫变成**声明**（治 M105 教训）；
3. **hooks 归一**：v2 的 30+ 个 `skills::xxx()` 钩子函数归一为 `Hook` 枚举 + 注册表（治「各写一半」）；
4. **steps 有序**：多阶段技能的「然后」顺序写入 steps（治箜声时序类缺陷）；
5. **授予技一等公民**：怀柔/清侧/排异/攻心等都进 SkillDef（治授予技漏注册）。

### 6.4 扩展路径（20 批次 + 已知未完成武将 + 未来）

- **新增武将技能**：写一个 `SkillDef`（声明式），注册进 `SKILLS`，机制缺口由 `sgs2-batch-scaffold` 类工具显式报 `❓`。
- **扩展范围（2026-11-13 裁定）**：**仅非国战、非下线（offline）** 的武将技能。
  国战是另一种游戏，引擎可能完全不沿用，**不在 V3 范围**；85 个 offline 原版（被界/将去重排除）也不在范围。
  范围 = 147 live（B0–B20）+ 未来新增非国战武将。
- **新增装备**：注册 equip-skill（§5.3）。
- **新增牌**：牌表生成物加属性字段（伤害属性/响应牌/是否伤害锦囊），内核零改动。

### 6.5 与 v2 的复用 vs 重写（继承 ADR-0042 / next-v3-rebuild §5）

| 复用 | 重写 |
|---|---|
| `cards_generated.rs` / `generals_generated.rs`（数据生成物） | 内核 `kernel/*`（zone/event/pending/resolve/flow/card_play） |
| 机制词表 49 条 + 775 裁定锚点 + 契约门禁脚本 | 技能层：从「handler」到「声明式 SkillDef + face」 |
| 视图契约 + Web 端（`apps/web`、`targetPicker`、pipeline） | 装备特效：从「散落牌结算」到「equip-skill」 |
| align 单 / 门禁脚本 / 用例口径（`ask_completeness`/`state_semantics` 等） | AI：从「启发式」到「规范接口 + RL 可插拔」 |

## 7. V3 复用 Web 页 + SB3/PPO AI 适配度评估

### 7.1 Web 复用策略（V3 优先，Web 适配）

- **端侧不动**：`apps/web` 的 `targetPicker`、三分区、`overlayKindFor` 映射、五谷/观星/拼点/蛊惑浮层**全部复用**；
  v2 已经做到「视图输出 v1 兼容字段 80/80」，V3 继续**输出同一视图契约**（`view-required.json` 80 字段）。
- **V3 优先**：V3 引擎先按「视图契约 + pending 描述符」产出，Web 只做**字段适配**（新增 kind 加映射），不改交互形态。
- **新增债务只许两类**：① V3 新 pending kind 的专用浮层（如未来新机制）；② 化身/蛊惑等特殊区（W2/W3 已在 v2 补齐，V3 复用）。
- 落点：`view.rs` 纯投影（I3），`special_zones` 开发前纳入契约。

### 7.2 stable-baselines3 + PPO 适配度（2026-11-13 按用户 PPO 蓝图重估）

> 用户提供了一份完整 PPO 工程蓝图（五阶段：沙盒封装 / Actor-Critic 网络 / PPO 流水线 / Self-Play 策略池 /
> 可观测监控 + 掩码边界 / 隐状态建模）。**结论修正**：PPO 不是「只配做完美信息子问题」，它就是目标本身。
> 该路线 = Suphx（麻将）/ Pluribus（德扑）/ DouZero（斗地主）验证过的「不完全信息 + 多智能体 → 自对弈 PPO +
> 隐状态 + 信念状态」。上一版把它归为 POMDP/非平稳/多目标「不匹配」是**过度悲观**——这些在蓝图里都有正确解法。

**五阶段 → 项目现状映射**：

| 用户阶段 | 内容 | v2 引擎现状 | V3 要补 |
|---|---|---|---|
| 一·沙盒 | reset/step + 序列化 + 合法性拦截 | ✅ `execute_action`=step；确定性 seed=可回放；**`legal_actions` 天然 = 物理规则掩码** | 观测张量编码、奖励信号、Python 绑定 |
| 二·网络 | Actor-Critic + Transformer | 不落引擎 | SB3 侧，依赖观测编码 |
| 三·PPO | Rollout / GAE / Clip | 不落引擎 | SB3 内置 |
| 四·Self-Play | 策略池 + Elo 采样 | 需支持「同局不同策略座位」 | 训练基建 |
| 五·监控 | 熵 / 价值损失 / 防刷分 | 决策日志已有（`check:sgs2-decision-log`） | 训练侧指标 |

**关键结论：用户「物理规则掩码 vs 博弈策略掩码」的边界，v2 引擎已经天然实现**——`legal_actions` 只做物理约束
（没杀不能出杀、距离不够不能指定），从不下发「内奸不能打反贼」这类策略约束。这正是「掩码只教 AI 活下来，
不教 AI 怎么赢」的要求，写进 V3 AI 契约。

**直接约束 V3 的三条**：

1. **动作掩码 = 物理规则**：V3 `legal_actions` 即 SB3 action mask，一字不改（= 宪法 I1 同一件事）。
2. **奖励只给终局**：反贼「主死=+1」/ 主忠「反内全灭=+1」/ 内奸「自己赢=+1」，中间奖励宁缺毋滥。
   这**简化**了「多目标」——多目标只体现为「奖励函数按身份不同」，不是网络同时优化多目标。
3. **隐状态建模**：V3 观测不能是「单帧裸状态」，必须是**按回合/座位组织的序列观测**（公开事件流：伤害/弃牌/亮身份），
   可喂 Transformer（每座位一个 token）。

**蓝图暴露但一句带过的四个真问题（V3 就要埋桩）**：

1. **观测张量序列化是硬骨头**：「固定格式数组」实际最难——160 张牌、可变手牌数、可变目标集。
   需要牌特征编码（花色/点数/类别/区域/是否公开）+ 变长 padding + 可见性掩码。schema V3 就锁，否则训练侧开不了工。
2. **内奸奖励（2026-11-13 用户澄清后修正）**：内/主/忠/反的终局奖励各按**独立胜条件**给（不是「内=主」同一函数）。
   「杀忠内正/主负」**不需手写塑形**——它自动来自 ① 主杀忠的环境规则惩罚（主弃牌）+ ② 终局归因（GAE 把最终胜负归到杀忠那一步）。
   内确实更难（无队友 + 必须亲手杀主 + 必须最后存活），但优势在信息差（内知道自己身份，主不知道谁是内）——
   对手池掺规则 AI 保证内奸有赢样本即可，不必重做奖励函数。
3. **局内确定性规则奖励**（杀反摸3 / 主杀忠弃牌）要不要进奖励函数？**建议进**（它们是确定性规则反馈，非塑形），
   但与环境奖励/终局奖励分层，别混进 GAE 优势造成信用分配污染。
4. **计算预算 + warm start**：独立项目别从零 self-play——先用现有启发式 AI（`ai.rs`）做**行为克隆蒸馏**成初始策略，再进 PPO。

**框架选型（2026-11-13 用户裁定）**：**SB3 + PettingZoo/SuperSuit + 参数共享**，不上 RLlib。
所有身份共用同一个 PPO 策略网络，输入带身份/血量/手牌/场上关系；PettingZoo/SuperSuit 把多智能体环境包装成
SB3 能吃的向量化环境。优点：单机可跑、接口干净、排查快，适合先把环境/特征/掩码/奖励/RNN 跑通。
SB3 边界（不原生支持 MAPPO/QMIX、不支持分布式、信用分配自设计）当前不构成瓶颈；
**RLlib 仅在单机采样成瓶颈、需要分布式训练时再评估**（不是必然迁移）。
V3 侧仍只锁「观测/动作/奖励 schema」+ Gym 风格接口，实现（SB3/PettingZoo）可替换。

**修订后建议路径（O5-C）**：

1. **V3 落地「RL-ready 三接口 + 观测编码」**：`Observation`（合法观测，ADR-0032 可见性不变量，序列化）/
   `ActionMask`（= `legal_actions`）/ `Reward`（终局按身份 + 局内确定性规则，分层）；Gym 风格、SB3 无关。
2. **验收后用 BC 蒸馏现有启发式 AI 做 warm start**（省 sample，且天然对齐人类可理解的打法）。
3. **再上自对弈 PPO**：SB3 + PettingZoo/SuperSuit 参数共享起步（PPO/MaskablePPO 都现成），RLlib 仅单机采样成瓶颈时再评估。

> 结论：**PPO 是目标，不是子问题实验；但 V3 的 AI 交付物仍是「RL-ready 接口 + 观测编码」而非「PPO 实现」。**
> 把「适配度」问题变成「观测/掩码/奖励 schema 是否完备、是否 SB3 无关」的可验收项。

## 8. 补充遗漏（用户点 8）

在用户 8 点之外，本次收集额外发现：

1. **贞良转换技的 yang/yin window 在注册表里是 null**——转换技导出本身有缺口，V3 的 face 化要一并修。
2. **怀柔/清侧/排异三个授予技：有 Web 文本、无效果实现**（只在 `skill-text.ts` 补丁 + `granted.push(code)`，
   注册表无对应 SkillDef、无 handler）。这是「授予技非一等公民」的直接证据——**授予了 code 字符串，但效果本体没写**。
   与之对照：攻心/荐言/急袭/思蜀/和弦/柔弦/烈弦/激弦 8 个授予技**已注册已实现**（`specs/sanguosha/skills/granted.md`）。

   **2026-11-13 已对齐（权威描述，V3 按 O2=A 实现为一等公民授予技）**：
   - 怀柔 `huairou`（破势觉醒授予，**仅授予自己**）：出牌阶段可**重铸**一张装备牌（弃置并摸一张）。
   - 清侧 `qingce`（鸿举觉醒授予，**仅授予自己**）：出牌阶段限一次，你可以弃置一名角色一张牌，然后若你与其的距离大于 1，你摸一张牌。
   - 排异 `paiyi`（自立觉醒授予）：出牌阶段限一次，移去一张「权」，令一名角色（含自己）摸 2 张；若其手牌数大于你，你对其造成 1 点伤害。
3. **`triggers` 字段只覆盖「事件型」触发**，而 v2 还有 30+ 个「钩子型」能力（conversions/target_blocker/distance/sha_limit/dying/wuxie/flip…）不在注册表分类里——V3 的 `Hook` 归一化正好补上这个「分类盲区」。
4. **「非技能规则面」清单**（大厅/身份/中断/选将/武将包/视图字段）历史上不在对齐单里，是 v2 迁移漏项的最大来源（§4.2）——V3 必须单独一张清单。
5. **房规（终局 round>100 回血失效）** 是引擎内非官方规则，V3 要作为显式配置项继承，不能丢。
6. **伤害事件需「属性 × 来源」二维模型**（2026-11-13 藤甲裁定引出，用户补充）：
   `damage_kind`（fire/thunder/normal，属性）与 `source_kind`（slash/nanman/wanjian/duel/skill/hp_loss，来源）是**两个正交维度**，缺一不可。
   「普通杀无效」= `source_kind==slash && damage_kind==normal`；火杀=slash+fire（藤甲+1）；雷杀=slash+thunder（正常）。
   转化/虚拟牌按**生效定义**定属性（朱雀羽扇普杀→火杀=fire；武圣红牌→普通杀=normal；龙胆闪→杀=normal）。
   **每个造成伤害的技能/牌必须声明 damage_kind**（雷击=thunder、焚城/火攻/朱雀=fire、其余=normal）——
   这是 §2 技能分类当前遗漏的维度（分类只按触发形状，没按「伤害属性」分类）。
7. **白银狮子需「离开装备区」钩子**：离开装备区（弃置/移动）回复 1 体力 = 装备流失钩子（`on_equip_lost`，枭姬同源）——
   证明 equip-skill 需要订阅「装备移动」事件，不只「伤害」事件。
8. **回放/对拍**：v1 已删，V3 的行为 oracle 从 git `f8a7db3^` 复活 v1 为 test-only（ADR-0042 M0），这是唯一能防「语义漂移」的锚点，必须 M0 就做。
9. **陷嗣「他人侧」 + 「非主公技他人侧/授予」全量检索结论**（2026-11-13 用户裁定 + 检索）：
   - **陷嗣裁定**：按原文「使用」只覆盖**主动 + 借刀**，**不覆盖**决斗/南蛮的「打出」场景——v2 现状（只 `mode:use` 主动入口）**即正确**，无需补响应窗口。
   - **非主公技「他人侧可发动」全量 = 2 个**：陷嗣（其他角色移逆出杀）、蛊惑（其他角色质疑）。两者 v2 都已实现，**无新增遗漏**。
   - **非主公技「授予」全量**：授予技 11 个（攻心/荐言/急袭/思蜀/和弦/柔弦/烈弦/激弦 **已实现**；怀柔/清侧/排异 **未实现效果**）+ 授予标记 2 个（遗礼橘/武烈烈，已实现）+ 借用主公技 1 个（伪帝，已实现）。
   - **主公技他人侧 = 13 个**（已由 LordSide 注册表覆盖，ADR-0041）。
   - **机制结论**：v2 只有主公技有 `LordSide` 注册表，**非主公技的他人侧（陷嗣/蛊惑）与授予技（怀柔/清侧/排异）都是散落实现**。
     V3 需一个通用「他人侧/授予」机制，覆盖 主公技 + 陷嗣 + 蛊惑 + 化身 + 绝响 + 攻心 + 伪帝 + 怀柔/清侧/排异。
     这正是 O2=A（授予技一等公民）的完整落地范围。

### 11.3 纪律（防「报一个修一个」与长任务多批次漂移）

1. 每发现一个缺陷，必须归入某类并补该类门禁/扫描，再修实例（M105 已证正确）。
2. **差分对拍进 CI 常驻**（每次提交跑核心对拍），防长任务多批次漂移——这是防「多批次执行漂移」的最强手段，
   比「规格先行」更硬，因为它对拍的是 v1 oracle 的行为而非人的纪律。
3. 真机验收清单 R1–R7 是**关闭条件**；不在清单内的沉默风险，发现后先登记进 §11 再修。
4. SPEC 防漂移现有机制：`check:spec-conformance`（覆盖/锚点/注册表一致）+ `check:sgs-align`（冲突阻断/147 覆盖）+
   mechanics.json「机制版本变更触发跨批次冲突阻断」。这些管「规格↔实现一致」，**不管「分批执行节奏」**——
   节奏靠 ② 的 CI 差分对拍 + 每批 DoD 收口。
