# 计划：B8 回归测试

## 计划
- 目标：为 B8 需求建立可重复执行、结果稳定的回归测试集，覆盖此前已实现功能的既有行为，防止后续改动引入回退。
- 实施顺序：盘点现有测试资产 → 确认测试框架与入口 → 固化回归基线（固定输入夹具、固定随机种子、必要时快照）→ 补齐回归用例 → 接入一键命令与 CI → 输出回归清单文档。
- 分层策略：区分 smoke（快速、每次提交跑）与 full（主干/发布前跑），避免回归集膨胀后拖慢日常反馈。
- 可追溯性：每条回归用例标注对应需求/历史缺陷编号，便于失败时快速定位影响面。
- 不在本计划内臆定覆盖率门槛、用例数量或运行时长等数值约束，相关项见「待确定事项」。

## 待办实现
- [ ] 盘点仓库现有测试入口与配置（查找 `package.json` 的 scripts、`pyproject.toml`、`pytest.ini`、`vitest.config.*`、`jest.config.*`、`Makefile` 等），结论写入 `docs/testing.md`
- [ ] 建立回归测试目录 `tests/regression/`（若项目采用其他约定则按现有约定落位），并按模块拆分文件
- [ ] 为回归用例抽取共用夹具（固定牌堆/固定玩家/固定输入），集中放在 `tests/regression/fixtures/`
- [ ] 所有涉及随机性的用例改为固定随机种子或可重放输入，禁用非确定性来源
- [ ] 补齐 B8 对应的回归用例，每个用例文件内注明覆盖的需求/缺陷编号
- [ ] 增加一键运行入口：smoke 集与 full 集分别对应一条命令（如 `make test-regression` / `make test-regression-full`，或 package scripts）
- [ ] 在 CI 配置中接入 smoke 集（PR 触发）与 full 集（主干触发），失败时输出可定位日志
- [ ] 在 `docs/testing.md` 中维护回归清单表格：用例 ID、覆盖范围、对应需求/缺陷、运行层级
- [ ] 补充“新增回归用例”的操作说明，说明目录规范与命名约定

## 待确定事项
- B8 具体要覆盖哪些模块（规则引擎、牌堆/洗牌、回合流程、计分、UI 交互、存档等），以及是否有明确的历史缺陷清单？
- 项目现有测试框架与目录约定是什么（pytest / vitest / jest / 其他）？本计划中的路径为占位写法，需按实际约定调整。
- 是否已有 CI 系统（GitHub Actions / GitLab CI / 其他）？若无，回归集是否只保留本地命令？
- 回归集是否需要端到端/快照测试，还是仅单元与集成层？
- 桌游随机性的处理口径：统一固定种子，还是保留随机但支持失败重放？
- 是否存在既定的覆盖率门槛或“必须通过”的用例白名单？

## 验证事项
- [ ] 执行回归 smoke 命令（如 `make test-regression`），全部用例通过
- [ ] 执行回归 full 命令（如 `make test-regression-full`），全部用例通过
- [ ] 连续多次运行 full 集，结果一致，无非确定性失败
- [ ] 在任一模块中故意引入一处已知回退（临时改动），确认对应回归用例失败并能从日志定位到用例 ID
- [ ] 撤销上述临时改动后重跑，确认恢复通过
- [ ] 检查 `tests/regression/` 下每个用例文件都带有需求/缺陷编号注释
- [ ] 检查 `docs/testing.md` 的回归清单与实际用例文件一一对应，无遗漏或多余条目
- [ ] 如已接入 CI，触发一次 PR 流水线，确认 smoke 集执行且失败日志可读

## harness 优化项
- 统一夹具与固定随机种子，从源头消除 flaky 用例
- 失败输出结构化：日志中打印用例 ID、输入夹具名与关键中间状态
- 回归集分层运行（smoke / full），PR 只跑 smoke，主干与发布前跑 full
- 用例 ID 与需求/缺陷编号绑定，形成“失败即定位影响面”的追溯链
- 提供最小复现命令模板（单用例运行方式），缩短排查路径
- 回归清单文档与用例目录做一致性检查，防止清单腐化
