## 2. 暴露的设计缺陷（本会话反复踩坑的根因）

### 2.1 技能触发「就地压帧」与父帧 pop 冲突（命中 5 次）
- 现象：技能在别人的结算过程中 `push(Frame)`，父帧随后 `pop`，把新帧弹掉 → **技能永不触发 / 帧内牌丢失**。
- 本会话命中：明任替换、箜声（两处）、良姻（回血）、贞良（阴）。
- 现状对策：各自加「栈空队列」（`zhenliang_yin_queue` / `liangyin_heal_queue` / `kongsheng_use_queue`）。
- **缺陷**：这是逐点打补丁，没有统一「延后触发」机制 → 新增技能必然再踩。

### 2.2 帧里暂存牌 = 隐形丢牌源
- 现象：牌从区域取出、暂存在 `XxxFrame.cards`，若帧被丢弃/替换，牌从所有区域消失。
- 已修：箜声三处 + 守恒统计（`in_frames`）。
- **缺陷**：没有「帧持牌必须落盘」的强制约束（无类型层面的 owner 概念）。

### 2.3 「移出/移入游戏」原先 7 处硬编码（本次已抽象为事件）
- 旧：`屯田/权计/箜声×3/to_void_card/from_void_card` 各自手写 `liangyin_trigger`。
- 新：`skills::add_mark` / `remove_mark` / `turn::to_void_card` / `from_void_card` 统一上报
  `state::CardMoveEvent`，`advance` 在栈空派发 → 良姻订阅。**技能不再硬编码触发点**。
- **仍未覆盖**：延时锦囊（小乔♦当乐不思蜀、徐晃黑牌当兵粮寸断）的「移出/移入」——
  另：事件全局产生，**技能需自行按「生效窗口」过滤**（良姻/箜声已加「仅周妃回合内」门闩，复验 35）。
  判定区（`judge_zone`）的进入/离开没有统一钩子（散落在 `resolve.rs:2389/2399/3532`、`resolve_fire.rs:948`、
  `resolve_forest.rs:531`、`resolve_wind.rs:834/840`、`resolve_yijiang5.rs:722`、`resolve_sp2.rs:2188`…）。
  对良姻而言可达场景是**周妃自己判定阶段**延时锦囊判定后进弃牌堆（=移入）。

### 2.3b 「使用/打出 → 弃牌堆」也是硬编码（第 4 次漏接线）
- 贞良（阴）依赖「回合外使用/打出的牌进入弃牌堆」，实现是在各使用路径手写 `queue_zhenliang_yin`：
  已接 基本牌/装备、锦囊、响应打出、**濒死【酒】自救、濒死【桃】/急救、无懈可击**（复验 36）。
- 缺口仍然存在：重铸、其他技能内的「视为使用」等路径未接。
- **根治**：`turn::to_discard_card` 作为唯一出口上报 `CardToDiscard { actor, card, cause }`，技能订阅事件，不再逐路径接线。

### 2.4 `pending` 缺统一「放弃出口」
- 现象：`target`/`choice` 类 pending 有时没有 `pass` → 客户端只能去点「结束出牌阶段」等不相关按钮 → 动作非法报错。
- 已修个案（良姻回血、贞良阴、箜声装备）。
- **缺陷**：pending 生成点分散（~50 处 `Pending { .. }`），没有「必须有放弃出口」的构造器/门禁。

### 2.5 视图白名单硬编码
- 转换技清单硬编码 → 漏 `zhenliang`（已改为 `skills::TRANSFORM_SKILLS` 单一事实源）。
- 同类风险：`view.rs` 里其它「技能清单」式白名单、Web 端 `optionButtons` 前缀白名单（漏前缀 = 浮层空列表）。

### 2.6 技能文本来自官网生成物，授予技缺失
- `skill-text.ts` 由 `heroes.json` 生成（只含武将自带技能）→ 怀柔/清侧 无描述。
- 已加 `GRANTED_SKILL_TEXT` 补丁表，但**机制上仍会漏**（新授予技必须人工补）。

### 2.7 虚拟牌/转化牌 无统一抽象
- 现状：`virtual_defs`（国色）、`skills::conversion_for`（武圣/龙胆/急救/酒池…）、各技能自建
  `skill:<code>:<card>` 动作 —— 三套并行。
- 与「移出/移入」「使用/打出」「响应」组合时需要穷举，难以证明覆盖完整。
- 用户 2026-11-05 指出的漏项：小乔方块牌当【乐不思蜀】、徐晃黑牌当【兵粮寸断】→ 属于虚拟牌 + 判定区 双重耦合。

### 2.8 结算顺序靠人记
- 箜声必须 ①取回→②良姻→③回血→④使用装备；良姻回血必须在奋激之后；奋激在栈空统一问。
- 现状：写在对应用例注释与 `rules-rulings.md`，没有「时序表」进代码结构。
- 建议：多阶段技能在 `skills.md` 里一张时序表 + 每个时序点一条回归（本会话对箜声已这样做）。

## 6. 【重要】技能文本歧义 → 期望不一致（本会话新增，必须纳入重构与验证流程）

### 6.1 问题性质

官方技能描述**存在歧义**，而实现只能选一种解读。**agent 不能自行裁定**（这正是全武将验证流程要求「人工确认期望」的原因，
见 `next-general-audit.md` §4.0）。歧义若未被登记，就会表现为「实现与用户期望不一致」，而且**每次走查都可能重新吵一遍**。

### 6.2 典型案例（本会话真实发生）

> 良姻：「当**每回合**首次有牌移出/移入游戏后，你可以与一名其他角色各摸/弃置一张牌，然后你可以令其中一名手牌数为 X 的角色回复 1 点体力（X 为『箜声』牌数）。」

- 歧义点：「每回合」= **所有玩家的每个回合**，还是**周妃自己的回合**？
  - 解读 A（字面）：任一名角色的回合内首次移出/移入都算 → 别人的回合也要问周妃。
  - 解读 B（用户裁定）：**只在周妃自己的回合内生效**（等价于回合开始挂勾子、回合结束摘勾子）。技能描述**没有写明**这一点。
- 影响：把「移出/移入」做成全局事件后，**开局明任置「任」也触发了良姻** —— 就是解读选错的直接后果（复验 35 已修）。
- 处置：`liangyin_trigger` 加门闩 `st.turn == owner && st.phase == Phase::Turn`；
  `skills.md` 明确标注「技能描述未写明，按用户裁定限定为周妃回合内」；`rules-rulings.md` 复验 35。

### 6.4 建议机制（重构时一并落地）

1. **新增歧义台账**：`docs/games/sanguosha/rules-ambiguities.md`
   字段：`技能 / 官方原文 / 歧义点 / 候选解读 / 用户裁定 / 裁定日期 / 实现落点(file:line) / 回归用例 / 状态(待裁定/已裁定)`。
   - 与 `rules-rulings.md` 的分工：rulings 记「裁定内容」，台账记「歧义本身 + 实现落点」，便于审计是否**每处都落地**。
2. **流程前置**：全武将验证的「文本审计」阶段，先把该将技能的歧义登记进台账（未登记者不得进入机器/人工走查）。
3. **实现契约**：歧义裁定必须在代码里以**显式门闩/常量**体现（如 `st.turn == owner`），并留注释指向台账条目；
   禁止「隐式按直觉实现」。
4. **门禁**：`check:sgs-general-*` 增加一项 —— 台账里 `已裁定` 的条目必须能追到回归用例名（防「裁定了但没实现/没测」）。
5. **重构影响**：事件的「生效窗口」必须参数化（谁在什么窗口内响应），不能由事件本身决定；
   参考良姻的教训：**全局事件 + 未定义窗口 = 误触发**。

## 7. 【决策项】是否引入 spec-kit / 规格驱动开发

### 7.1 背景（用户判断，2026-11-05）

> 「武将技能的实现难以接受，批量武将验证难以推进，对项目进度造成严重影响；如果技能不能按期望落地，
> 很难再推进之后的中期 AI 落地，甚至之前的一阶段 AI 都可能存在问题。」

本会话事实：B2 只有 8 将，一天内修了 **13 个缺陷**，其中 **4 次是同一类「触发点漏接线」**
（权计→良姻、良姻回血、箜声时序、贞良→使用/打出路径）。最后一次才改成**通用动作差分**（不枚举路径）。

### 7.2 要评估的问题

1. 是否需要引入 spec-kit（或等价规格工具）：把「技能文本 → 裁定后的时序表/触发契约 → 代码 + 用例」做成**强约束流水线**？
2. 若引入，落地形态是什么、维护成本多大、与现有 `skills.md` / `rules-rulings.md` / `rules-ambiguities.md` 如何分工？
3. 若不引入，用什么替代来保证「技能按期望落地」（门禁 + 模板 + 代码约定）？

### 7.3 候选方案

| 方案 | 做法 | 优点 | 风险/成本 |
|---|---|---|---|
| A. 不引入工具，强化约定 | 每技能一张「时序表 + 触发契约 + 回归映射」写进 `skills.md`；门禁检查“已实现技能必须有契约条目与回归用例” | 零依赖、渐进 | 靠人守，容易漂移（本会话已证明） |
| B. 轻量规格文件 + 生成器 | 每技能一个 YAML/MD 规格（触发事件、窗口、前置条件、时序步骤、期望断言），脚本生成：注册表骨架、用例骨架、文档表格；门禁校验实现引用 | 可校验、可与台账打通 | 需要设计 schema + 生成器（约 1–2 周） |
| C. 引入 spec-kit（或类似） | 用现成规格工具管理「规格 → 任务 → 实现 → 验收」 | 流程完整、可审计 | 引入外部工具/流程负担；与本仓文档体系可能重叠 |

**倾向（待用户定）**：先做 **B**（轻量规格 + 生成器 + 门禁），把本会话的 4 类反复踩坑（触发点、窗口、时序、放弃出口）
变成**规格里必填字段**，再评估是否需要 C 的流程能力。

### 7.4 与技术重构的关系

- 规格层解决「**按期望落地**」；重构解决「**能按规格落地**」（事件总线、统一延迟派发、VCard、Pending 出口）。
- 两者必须一起推进：只有规格没有基础设施 → 规格写不出来（无法表达）；只有基础设施没有规格 → 重现本会话的漏接线。
- 建议新会话的工作顺序：① 规格 schema 草案（B）→ ② 用 3 个技能（良姻/箜声/贞良）做试点 → ③ 再动手改基础设施 → ④ 回 B2。

### 7.5 附：本会话已把「枚举路径」改成「通用差分」的案例

贞良（阴）此前在 6 条使用/打出路径上逐条 `queue_zhenliang_yin`，濒死【酒】自救漏接 → 用户指出后改为：
`lib.rs::execute_action` 在动作前后做**手牌差分**（与奋激同一机制），判定条件：
「回合外 + 本动作有手牌离开手牌且进入弃牌堆（且动作不是 discard/recast）」→ 入队，栈空后询问。
**这是「不枚举场景」的正确范式**，重构时应推广到所有「使用/打出/失牌」类触发。

## 8. 【缺陷模式】同一规则在两处各写一半（本会话反复命中）

> 归纳自 2026-11-05 全程：技能行为被拆成「声明/状态/钩子/入口/视图」多个层次，**每层各自实现一半**，
> 任一层漏了都表现为「技能看起来实现了但就是不生效」。这是比「硬编码触发点」更隐蔽的一类。

### 8.1 本会话样本（全部已修，留回归）

| # | 规则 | 写了一半的地方 | 漏的另一半 | 症状 | 回归 |
|---|---|---|---|---|---|
| 1 | 决堰·宝物栏「本回合获得集智」 | `act_jueyan` 写了计数器 `jueyan_jizhi` | 集智钩子只认 `skills::has(seat,"jizhi")`，**不认计数器** | 显示"获得集智"，用锦囊不摸牌 | `p78::jueyan_treasure_grants_jizhi_this_turn` |
| 2 | 明任「开局置任」 | `init_mingren` 弹 MultiSelect | `min=0` **允许取消** → 「任」为空 → 明任/贞良**下游全废** | 两个技能整个失效 | 开局必选（`min=1`） |
| 3 | 清侧「出牌阶段可用」 | `turn.rs` 执行分支 + `Frame::QingCe` + `step_qingce` 都写了 | `legal_actions` **没下发** `skill:qingce` | 按钮不出现，无法手动使用 | `legal_actions` 补条件 |
| 4 | 鸿举「玩家选牌替换荣」 | `MultiSelect(min=max=荣数)` 写了 | 沙盒全 bot → AI 代选，玩家看不到选择 | 误判为「随机替换」 | `p78::hongju_swap_uses_player_selection` |

**同类历史样本（更早）**：
- 骄矜：legal 选项含装备区牌，**执行端只认手牌**（legal/execute 不一致）
- 缔盟：legal 不过滤费用，**execute 校验费用**（先选后报错）
- 急救：legal 提供红【酒】当【桃】，**execute 先按酒自救拒绝**
- 诫训/品第：动作 id 存在但 handler 未接
- 视图：转换技白名单漏 `zhenliang`（引擎有状态、视图不认）

### 8.2 成因

1. **同一语义有多个存放点**：`skills::has` / `flags` / `turn_counters` / `marks` / `marks_count` / `GrantedSkill` 六种
   「我现在有这个技能/状态吗」的表达方式，钩子只查其中一种；
2. **合法动作与执行分离**：`legal_actions`（给 UI）与 `act_*`（校验执行）各写一份条件，天然漂移；
3. **视图是第三份**：`view.rs` / 前端白名单再抄一遍（转换技、技能清单、pending 前缀）；
4. **没有「一致性门禁」**：以上任一处漏写，编译通过、测试不覆盖、机检（L1）也可能触达不到。

### 8.3 建议机制（并入重构范围）

1. **单一状态源**：统一 `SkillStatus`（自带/授予/本回合临时）查询接口 `skills::active(st, seat, code) -> bool`，
   所有钩子只调它；`flags`/`turn_counters` 里的「技能性状态」全部迁移过去；
2. **legal/execute 同源**：动作条件写成**一个函数** `can_<skill>(st, seat) -> Option<Action>`，
   `legal_actions` 与 `act_*` 都调用它（legal 提供 id，execute 再校验一次同一函数）；
3. **视图派生**：技能/转换态/动作前缀由注册表 + `Action` 列表派生，禁止手写白名单；
4. **一致性门禁**：脚本扫描
   - 每个 `skill:<code>` 动作 id 必须有 handler（已有类似检查，需覆盖所有前缀）；
   - 每个「授予技」必须在 `active()` 里可达（禁止只写 flags/counter）；
   - 每个 `MultiSelect` 的 `min/max` 与下游「取消后是否可用」要有明确断言；
5. **回归口径**：每个技能至少一条「**能看见 → 能点 → 点了生效**」的链路用例（不是只断言内部状态），
   这条正是本会话 4 个 bug 都能被测出来的原因。

### 8.4 【第 5 类】用户可见文案与语义相反 / 模糊

- **案例**（2026-11-05 复验 39）：无懈结算文案
  ```rust
  if cancelled { "效果被抵消" } else { "效果生效" }   // cancelled = 无懈层数为奇数 = 锦囊被抵消
  ```
  `cancelled=false`（**无懈被反无懈抵消、锦囊照常生效**）时打印「效果生效」→ 读起来像「无懈生效了」，
  与 `cancelled=true` 的「被抵消」形成**语义相反但措辞相近**的两条日志。
  结果：**正确行为被判成 bug**（用户报「火攻已无懈仍亮牌」，实测引擎正确，见 `p78::huogong_negated_by_wuxie_does_not_reveal`）。
- **代价**：走查里最贵的一种误判 —— 双方都信日志，agent 会去"修"本来对的逻辑，越修越乱。
- **建议机制**：
  1. 文案由**状态机直接生成**（如 `WuxieOutcome` 枚举 → 文案表），禁止在分支里手写整句；
  2. 文案必须自带**判定依据**（例：无懈张数 N、奇数=锦囊被抵消），让人能复核；
  3. 同类高风险文案：弃牌原因（已做过一次「手牌 X / 上限 Y / 原因」改造）、pending 提示、判定（红/黑桃）结论、技能触发与否；
  4. 门禁（可选）：日志断言类回归优先用「决定性片段」（如 `锦囊被抵消`），少用整句，避免文案改动造成大面积红。
