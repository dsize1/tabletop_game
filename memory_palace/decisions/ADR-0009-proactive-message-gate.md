# ADR-0009：主动消息开发门禁（proactive 须人工确认）

- 状态：已接受（Accepted，2026-10-17 用户裁定）
- 日期：2026-10-17
- 关联：`docs/conventions/coding-standards.md`、`docs/conventions/external-constraints.md`、`docs/modules/agent-gateway.md`、`.pi/skills/plan-workflow/SKILL.md`

## 背景

QQ 官方对**主动消息**（无 `reply_msg_id`）有严格配额与频控：群 1000 条/群/天、60 qpm（未认证 30）、单关系 20 qpm、每秒 ≤5。被动回复则在 5 分钟窗口内、每条消息最多 5 次（`msg_seq` 递增）。

游戏/聊天场景中，若默认使用主动消息，容易触达配额、打扰群成员，甚至导致封禁。需要把「主动消息」从默认手段变成**需要人工审批**的手段。

## 决策

1. **主动消息默认禁用**：agent-gateway 的被动回复超限（同一条消息第 6 次起）默认**丢弃并告警**；仅当 `PROACTIVE_MESSAGES_ENABLED=1` 时才降级为主动消息。
2. **开发门禁**：任何落地方案/计划若包含主动消息（`pushActive` / 无 `reply_msg_id` / 文案出现「主动消息」），必须：
   1. 在计划「待确定事项」列明用途与配额影响；
   2. 经**人工明确确认**；
   3. 在计划文档写入标记 `【主动消息已人工确认】`；
   4. 通过 `npm run check:proactive-gate`。
3. **优先被动回复 + 合并/聚合**：游戏每个动作的「模板 + LLM 叙事」合并为**一条**被动回复；多人/机器人动作尽量聚合，避免超过每条消息 5 次被动回复上限。
4. 门禁脚本 `apps/scripts/check-proactive-gate.mjs`（根/ apps 的 `check:proactive-gate`）检查最新计划或指定文件。
5. plan-workflow skill 把该门禁列为**硬性约束**。

## 理由

- 被动回复足以覆盖游戏与聊天；合并消息能显著减少条数（1 人 + 3 机器人 = 4 条/回合）。
- 主动消息配额昂贵且不可预测（日配额/频控），应由人决定是否使用。
- 门禁脚本提供**机械校验**，避免只在文档里写约定而无人执行。

## 影响

- 游戏动作反馈：每个动作一条消息（含结果、局面、下一步指引、牌面页；LLM 叙事合并其中）。
- 被动回复第 6 次起默认丢弃（日志告警）；需要时可显式开启 `PROACTIVE_MESSAGES_ENABLED=1`（须先通过门禁确认）。
- 既有 dev 任务的主动推送（计划短链）保留；**新方案不得默认引入主动消息**。
