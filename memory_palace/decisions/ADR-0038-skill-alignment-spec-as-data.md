# ADR-0038：技能规格「对齐单 + 规格即数据」（不引入 spec-kit 工具链）

- **状态**：Accepted（2026-11-06，用户裁定）
- **相关**：ADR-0016（引擎内核与技能事件总线）、ADR-0023/0028/0029（各包技能机制）、
  `memory_palace/plan/next-skill-abstraction-audit.md`（§6 歧义、§7 spec-kit、§8 缺陷模式）、
  `docs/games/sanguosha/align/README.md`、`docs/games/sanguosha/spike-report.md`
- **结论一句话**：技能的「期望」用**人可读对齐单 + 机可读规格（JSON）**固化，配门禁与架构不变量；
  **不引入** GitHub spec-kit 或同类流程工具链。

## 背景

1. 2026-11-05 B2 走查一天修 13 个缺陷，其中 4 次是同一类「触发点漏接线」、5 次「就地压帧被父帧 pop」，
   根因是设计耦合而非「文档没写清」（见 `next-skill-abstraction-audit.md` §2/§8）。
2. 官网技能描述本身存在歧义（良姻「每回合」、奋激「获得」、放逐 X 上限…），
   agent 不能自行裁定，否则必然出现「实现与期望不一致」。
3. 2026-11-06 发现文档长期写「149 将 / 83 排除」，实测为 **148 / 84**（张昭张纮同名勘误）——
   说明**手写事实**是漂移主因；spec-kit 的产物同样是手写自然语言，不解决这个问题。
4. ADR-0016 §4 与 `state-machine.md` §3.1 早已规定「技能经钩子接入、核心流程不写武将名分支」，
   但代码漂移未被任何门禁拦截 → 说明真正缺的是**可执行不变量**，不是更多规格文本。

## 决策

1. **对齐单为技能期望的唯一载体**（每批一份，`docs/games/sanguosha/align/<B>.json`）：
   7 段 = 官方原文（自动取自 `data/heroes.json`）/ 现实现分步陈述 / 与原文差异 /
   疑点+候选+倾向+影响面 / 机制依赖 / **动画·UI 期望** / **对齐后描述（权威）**。
   人读版 `<B>.md` 由脚本渲染（勿手改）。
2. **流程纪律**（借 spec-kit 三条，不引工具）：未对齐不得实现；验收标准先行（正例 + **反例**断言）；
   constitution = 架构不变量（`check:sgs-arch` / 内核门禁用例）。
3. **不引入 spec-kit 工具链**：其产物为自然语言，治不了「同一规则两处各写一半」；
   450/288 技能 × feature 目录的维护成本与既有 `skills.md` / `rules-rulings.md` 重叠。
   若未来需要，仅在**批次粒度**（21 批）借用其模板。
4. **规格即数据**：对齐单 JSON 由生成器渲染文档、生成用例骨架、驱动门禁（`check:sgs-align`），
   实现侧只引用条目编号，不复制描述。
5. **冲突阻断**：机制词表（`align/mechanics.json`）版本变更 / 同一术语异义 / 同一时序两步矛盾
   → 该批 `blocked`，门禁失败直到人工复核；行为级冲突由「旧批次回归必须全绿」兜底。
6. **计数类事实**（将数/技能数/预设人数/用例数）一律由脚本生成或校验（`check:sgs-counts`），禁止手写。

## 理由（取舍）

| 方案 | 结论 |
|---|---|
| 不引入工具，仅强化约定 | 否：B0–B2 已证明「靠人守」会漂移 |
| GitHub spec-kit / 同类规格工具 | 否：产物不可执行；与既有文档体系重叠；无助于 §8 类缺陷 |
| **对齐单（人读）+ JSON 规格（机读）+ 门禁 + 架构不变量** | **采纳** |
| 全量重写引擎后再补规格 | 否：规格与内核必须同步推进（只有规格写不出可表达的结构；只有内核会重现漏接线） |

## 影响

- 新增门禁：`check:sgs-align`、`check:sgs-counts`、`check:sgs-retire`、`cargo test -p sanguosha2`。
- 新增流程成本：每批一次「疑点汇总」人工裁定（默认同意 + 只答疑点）。
- 旧 crate 退役计划：`docs/games/sanguosha/legacy-retire.json`（B20 验收 + 30 天 / 硬上限 2027-01-31）。
- 反向约束：**不得**再把技能期望写在代码注释或散落文档里作为唯一来源；散文只能补充。

## 依据与验证状态

- 148 / 84 / 232 计数：由 `apps/scripts/lib/sgs-catalog.mjs` 实测（已验证，`check:sgs-counts` 门禁）。
- 「6 类缺陷可被结构性消除」：`apps/scripts/../sanguosha2` spike 15 条用例（含 6 条门禁）实测通过（已验证）。
- 「LOC 收益」：实测每技能专属代码只降 13%（未达 50%），**不作为决策依据**（见 `spike-report.md` §1）。
- 外部约束（QQ 频控/窗口）本 ADR 不涉及。

## 2026-11-11 复核（V2 技能自检后）

**触发**：V2 全量替换后发现 4 类「应在上轮收口」的欠账（技能类型元数据丢失、技能层直写体力、
可见标记未投影、内核技能名残留），且这些欠账在 ADR-0038 的「对齐单 + 门禁」体系下**没有报警**。
用户要求再次评估是否需要 spec-kit，并指出「规划定义了但无法实施 = 沉默风险」。

**结论：维持「不引入 GitHub spec-kit 工具链」，但把「规格即数据」推进到可执行 schema（原 §7 方案 B）。**

理由：
1. spec-kit 的产物仍是自然语言规格，无法解决本轮实际缺陷（字段缺失 + 门禁范围不足）；
2. 本轮欠账的共同点是「规格里没有这个字段 / 门禁不校验这个字段」，不是「文档写得不够」；
3. 已有对齐单 JSON 是天然的规格载体，扩展成本低于引入新工具链。

落地要求（新增）：
- 对齐单每个技能增加可执行字段：`kind`、`triggers/window/subject_window`、`mandatory` 步骤、
  `visible_marks`、`rulings[].test`（裁定→用例锚点）；
- 生成器从 schema 产出：注册表骨架、用例骨架、走查单类型/标记列；
- 门禁校验「已声明 ⇒ 已实现/已投影/有用例」，缺一即失败（把沉默风险变成红灯）。

复核周期：新增桌游引擎 / 单引擎技能数 >500 / 外部协作者 >3 时重新评估是否引入工具。
